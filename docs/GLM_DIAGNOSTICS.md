# Private GLM phase diagnostics

Set an optional absolute `diagnostics_path` in the owner-pinned GLM factory configuration to enable the existing PrivateDiagnostics sink. It must be a fresh file under an owner-only directory outside repositories. Successful close leaves an empty mode 0600 file; the first stream failure records a single bounded receipt. No failed or frozen stage is retroactively changed by this option.

Fixed phases separate `glm_prepare`, `glm_count`, `glm_budget`, `glm_admit`, `glm_dispatch`, `glm_receive`, `glm_parse`, and `glm_usage`. Integer fields report counted candidate input, admitted input, cumulative tokens already used, the session budget, and whether local completion dispatch occurred. Counted input can exceed remaining budget while admitted input stays zero. `request_dispatched:1` means the owned HTTP child received the completion request payload, or a completion event was observed; it does not prove server acceptance, native inference completion, or successful cancellation. No prompt, response, token ID, tool name/argument, tensor, exception message, local variable, source line, full path or arbitrary object is recorded. Stack frames and exception classes use the existing explicit allowlists.

Cumulative token rejection now raises the existing typed WorkerError `LIMIT`, including when the prompt leaves no room for an output token. WorkerSession exports only that code on its ordinary private protocol; detailed numeric accounting remains solely in the owner diagnostic file. Malformed native token-count results retain ordinary failure classification and are distinguished by phase. Engine admission, native transport and local chat parsing errors can likewise be distinguished without copying their payloads.

The regression uses a first successful turn with 9,212 input tokens and 131 output tokens, then a second count of 10,658 against a 20,000-token cumulative cap. It verifies a LIMIT error at used 9,343, admitted 0 and dispatched 0, with exactly one completion request. This tests the proposed failure mechanism, not the unrecorded second token count from the historical room. That run's read-only log evidence showed two successful tokenizations and one completion, no server exception stack, and no token-count log metadata; its precise cause remains unconfirmed. No model rerun, budget change or serving mutation is part of this ticket.
