# Restricted stock Duo orchestration qualification

The actual installed OMP 18.2.6 executable runs stock Duo task/hub/todo orchestration with two synthetic backends through the actual Python WorkerSession/worker_stdio core, under a deliberately restricted room guard. This qualifies provider inheritance, session routing, tool-result delivery, and bounded shutdown only; it is not the full stock Duo baseline. It is not a real GLM/Qwen coding result or activation-only Drift evidence.

Stock Duo source: `/home/example/Documents/Codex/2026-08-25/i-added-omp-harness-and-want/omp-local-duo`, commit `8aeb53d3377928874e364bc6f6f8a05b471983cc`, v0.5.1. The probe copies its src and duo-peer agent unchanged into a scratch directory; an extension proxy invokes its actual registered command. OMP executable SHA256 is `d498da40d577e1ffa681ca8632c2ea40a9f722a08b880412011d37dffee9513a`; stock command.ts SHA256 is `ca699d1e07b273da2d95dac696c97d71d05aaa08260ea5fba91782097cf89e21`.

Two actual compatibility failures were reproduced. Child provider registration replaced the parent closure, now corrected by an owner-config-hash keyed shared process pool with explicit OMP session routing and session-scoped shutdown. Stock Duo also rewrites task arguments to append canonical todos and the controller strips intent metadata; the bridge now accepts only exact tool_execution_start receipts bound to the generated call ID/name. The original generated arguments remain in worker history and a counted control amendment precedes the tool result. Unobserved rewrites, unknown calls, changed tool names and receipt mismatches remain errors.

Developer messages include peer-authored Hub text. They and observed execution amendments are accepted only with explicit experimental_multi_turn and memory_mode=no-link, as declared text-Duo communication. Linked mode still rejects this path. Stock Duo source remains unchanged, but this qualification deliberately narrows its tool privileges: parent task/hub/todo, child hub/yield, checked both when advertising tools and before execution. The earlier version of this document incorrectly said the child had no file or shell tools: installed OMP inherited read/bash/edit and other defaults despite the parent CLI tool list, and an adversarial fixture successfully read a scratch sentinel. The new guard removes those tools and independently blocks their execution, limits dispatch to one pinned Duo peer in the exact scratch scope, and restricts Hub addressing to that peer. The existing OS sandbox denies network and private audit access and permits only scratch writes; this restricted test does not qualify project tools or a network-enabled task sandbox.

An asynchronous Hub update can wake either worker without a new user or tool result. The companion control-only runtime ticket consumes one pending control update, preserving turn/token/time limits without fake user replay. The fixture allows 4–6 parent and 2–6 child streams because the installed controller emits asynchronous advisories. It requires exactly one open/close per worker, no worker/controller error, different own-prompt hashes, parent task/todo authority and no child task/todo authority. Known controller-skipped calls are counted separately and retried within the same six-turn bound.

Observed guarded result: PASSED, exit 0, 1.264 seconds, parent six streams/four tool results/five own-control updates, child five streams/one tool result/four own-control updates, one explicitly counted skipped parent call, zero errors. Each worker opened and closed once; actual tool calls were todo once, task once and hub three times. Fixture token usage is synthetic, monetary cost and joules are unmeasured.
