# Native Qwen control serialization

The Studio checkpoint rejects a system-role message after an assistant turn. This was reproduced with its actual CPU tokenizer for both a completed assistant followed by a control-only wake and an assistant tool call followed by its tool result plus control. Both paths raised TemplateError before the fix; no model weights or inference were involved.

The Studio backend now selects the explicit `qwen-reader-user-v1` serializer when the checkpoint config declares `model_type=qwen4_exp`. This is a model-family-specific serialization choice, not a claim that system and user roles are equivalent. A control snapshot becomes a native user message whose text explicitly says it cannot replace or outrank initial system instructions and may contain peer-authored text on the declared text channel. The original leading system message and all consumed tokens remain unchanged. Unknown families retain their existing serializer and exact-prefix failure behavior; a family match does not waive runtime prefix validation.

The existing provider only admits developer/Hub text and execution amendments in the opt-in no-link/text-Duo path. This change does not loosen that boundary or put text on the activation transport. The protocol still bounds control updates, input bytes, turns, tokens and the absolute session deadline, while Studio counts every appended suffix. A pending tool group must finish before control is appended.

CPU verification used `/home/example/.omlx/models/Vontra/Qwen3.8-Flash-Next-MLX-4bit-MTP` with the installed oMLX Python 3.11 runtime and Transformers tokenizer, local_files_only=True and trust_remote_code=False. The probe imports tokenizer/configuration code only, with bytecode writes disabled, and sends program source through SSH stdin without staging files or touching serving processes. No tensor values or generated model text are inspected.

After the change, the completed-assistant case preserved all 274 cached prefix tokens and appended 59 tokens; the tool case preserved all 296 and appended 70. Both exact token-prefix comparisons passed. These are synthetic messages rendered by the real template, not evidence of real model reasoning, live cache parity or role-attribution quality. The next gate remains the bounded native Qwen tool/control continuation run under its owner manifest.

The reusable CPU command is `python scripts/omp/studio_control_template_probe.py --checkpoint CHECKPOINT`, in an environment containing that checkpoint tokenizer and this source tree. Initial normalization depends on codec commit `bfbbd3aeccdd753d6e98a30db34e017ded457c91`; bounded control-only wake depends on `889207dd795e40f4ba4449fb314400822e0a8fb5`. No energy or monetary cost was measured.

Validation: the two new constructor/serialization regressions first failed, then 27 focused codec/control/backend tests passed in 0.04 seconds. The full reference suite passed 544 tests with three existing adapter skips in 33.62 seconds; the next-runtime gate suite passed 155 with the existing sparse-indexer parity xfail in 8.00 seconds. Tests used the primary existing .venv and .venv-next Python executables with PYTHONPATH=. in the isolated worktree. The skips and xfail are not native gate passes.
