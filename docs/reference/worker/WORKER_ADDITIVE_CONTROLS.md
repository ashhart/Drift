# Additive own-control updates

The provider now sends `own_control_append` with `{system_prompt: string[]}` and expects exactly `own_control_append_ack` with an empty payload when a continuation adds control text to an unchanged base. The operation is private own input, never activation transport. The Python worker implementation is a paired dependency supplied by the parent integration ticket; an older worker rejects the new operation rather than silently treating it as a snapshot.

## Exact selection and ordering

The existing full history/receipt reconciliation, declared peer-text authorization, system-update opt-in and tool-configuration checks run first. Appending is selected only when the canonical base system blocks equal the previous accepted base and the previously accepted developer strings are an exact prefix of the current developer strings. The payload contains new developer strings followed by newly observed execution-receipt amendments. It is sent before fresh user/tool-result input, once per successful ingestion, and excludes previously delivered base, developers and amendments. No operation is sent when there are no additions. Native generated assistant history is unchanged, and the worker continues to count actual input/prefill under its existing byte/token/turn/time limits.

A real base change falls back to the existing full `own_control` snapshot, including current base/developers/amendments; after success this becomes the new append baseline. Historical developer rewrites already fail strict history reconciliation, and changed tools fail CAPABILITY; neither reaches an append fallback. The provider records its new base/control/history state after input delivery succeeds. Python retains the existing control authority: GLM native system context and Qwen explicitly reader-owned native user context; additive labels must not claim to supersede previous controls.
